# Shared Case DSL v1 authoring rules

These rules apply to existing Scenario Drafts and new Scenario Drafts created from a Suite.

- Use structured Tool fields. Do not generate YAML or invent Command names. A Tool success means the Draft already exists; read and modify that same Draft instead of recreating it.
- Copy each Step's `operation` from `getApiOperationSchema` result.operation.dslOperation. The platform reference is `operation.id`; method/path belong to `operation`. `request` contains only headers/path/query/body. A stable Draft Step ID is not a DSL Step field.
- Every HTTP Step has response.status: `{"operator":"equals","expected":201}`, `{"operator":"oneOf","expected":[200,201]}`, or `{"operator":"range","min":200,"max":299}`. Use the statuses declared by the API contract. An integer alone or a `code` field is invalid.
- Put assertions and extraction inside `response`. An assertion is `{"source":"response.body","path":"$.id","operator":"exists"}`. An extraction is a named map entry such as `"orderId":{"source":"response.body","path":"$.id"}`; never an array or a bare JSONPath string.
- Use `${variableName}` or `${variables.variableName}`. An extraction named orderId creates the flat variable `${orderId}` in subsequent Steps. Never use `{{variableName}}` or a Step-name namespace.
- `response.body` is the raw body. `decrypted.<name>` requires an enabled afterReceive Action producing that name. Before modifying a Draft's assertion or extraction, call getStepDataSources and copy an exact returned source. `raw` is never a source.
- Effective API processing settings may already encrypt the request and decode the response. Use business request data and `business.response.body` for the resulting business JSON; `wire.response.body` is an explicit raw-body alias. Do not add PGP Actions that duplicate API processing. The execution order is beforeSend → API request processing → afterRequestProcessing → HTTP → API response processing → afterReceive → assertions/extraction. Advanced `manual` or `wire` modes must be selected explicitly; do not silently replace configured API processing.
- For every selected Operation, read `getApiOperationSchema` and use `operation.authoring.request.schema` for request.body and `operation.authoring.responses[expectedStatus].schema` for business JSONPaths. These schemas expand local references and use effective platform overrides. `requestBody`/`responses` in the raw definition describe the wire protocol and may contain ciphertext envelopes. Do not guess fields from a summary or operation name, and do not stop at an unresolved `$ref`. Respect required fields, nested array item schemas, types, enums, bounds and additionalProperties. Declared examples are illustrative; obtain current resource IDs from a suitable API when needed.
- Response field names and Scenario Variable names are independent. For example, if the documented order response has `id`, extract `orderId` from `{"source":"business.response.body","path":"$.id"}` and use `${orderId}` in a later request's documented `orderId` field. Never infer a response field from a variable name or add the report's result name to a JSONPath. Request fields must come from that specific contract.
- Validation includes authored request and response-path checks against the selected API contract. Repair each ERROR before presenting the Draft. Intentional invalid-input tests expecting only error statuses may retain request-schema warnings; explain their purpose instead of converting them into positive tests.
- Read getScenarioDraft before resuming modifications. Use its latest revision and stable Step IDs in the Command Plan. On a revision conflict, read again; do not guess the revision.
- Correct a recoverable input error using its exact path and the declared schema. If the same repair still fails, explain the blocker and preserve the Draft instead of probing more field names.
- Once the Draft satisfies the request and validation succeeds, summarize the result and stop generating. User confirmation creates formal resources; a Draft alone has not been saved as a formal Scenario or executed.
